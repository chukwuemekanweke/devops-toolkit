# Deployment and manifest model

The application-owned [image configuration](image-configuration.md) is static build intent. This document describes the different, generated artifact that records one published release. Deployment and rollback consume the generated artifact and never treat the static configuration as proof that an image was published.

## Release versus environment

A deployment manifest identifies one immutable application release. It is generated by `docker-publish.yml` after every component has been pushed and its registry digest resolved. The same manifest can be promoted to multiple environments.

The manifest contains release identity only. Hostnames, SSH data, Compose files, ports, domains, environment variables, credentials, volumes, replica counts, and approval policy are environment configuration and must not be embedded in it.

Application repositories own their production Compose definitions and stack-specific health configuration. The toolkit owns the shared locked execution that applies those definitions to a provisioned VPS. Multiple applications coexist as independent `stack-name` values with separate paths, networks, ports, domains, volumes, history, and concurrency locks.

## Manifest schema v1

The machine-readable schema is [deployment-manifest.schema.json](schemas/deployment-manifest.schema.json). A representative four-component release is:

```json
{
  "schema_version": "1.0",
  "deployment_id": "0123456789abcdef0123456789abcdef01234567",
  "source_repository": "chukwuemekanweke/dotnet-core-project-template",
  "source_commit": "0123456789abcdef0123456789abcdef01234567",
  "build_reference": "https://github.com/chukwuemekanweke/dotnet-core-project-template/actions/runs/123456789",
  "created_at": "2026-11-21T12:00:00Z",
  "components": [
    {
      "name": "webapi",
      "image": "docker.io/example/backend-webapi",
      "digest": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    },
    {
      "name": "consumer",
      "image": "docker.io/example/backend-consumer",
      "digest": "sha256:bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"
    },
    {
      "name": "jobs",
      "image": "docker.io/example/backend-jobs",
      "digest": "sha256:cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc"
    },
    {
      "name": "migrator",
      "image": "docker.io/example/backend-migrator",
      "digest": "sha256:dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd"
    }
  ]
}
```

Component names are caller-defined stable logical identifiers. Docker Compose maps them to services; the toolkit does not infer that mapping from application names. Each deployable reference is constructed as `<image>@<digest>`. Tags may aid discovery but are never authoritative.

The manifest is canonicalized with UTF-8 encoding and stable key order before calculating its SHA-256 audit hash. It must never contain credentials, tokens, private registry auth, build secrets, SSH material, or application runtime secrets.

## Lifecycle

1. **Build:** image publishing validates input before login, pushes every component through an internal matrix, scans each published digest, and uploads one validated result artifact per component. A non-matrix aggregation job requires exactly the configured result set, emits the manifest as a run artifact, and exposes compact JSON for immediate orchestration.
2. **Initial deployment:** deployment validates the schema, pulls every digest, generates a Compose image override, verifies health, and records the manifest as active.
3. **History:** the target keeps append-only sanitized records plus immutable manifest copies. Environment metadata records who deployed what, when, from which workflow run, and the result.
4. **Reproduction:** a supported Compose configuration plus the manifest recreates the same application image set without source rebuild.
5. **Rollback:** a prior successful history entry supplies the exact digest set. Registry retention must keep those digests for at least the rollback window.
6. **Audit:** source commit, build reference, manifest hash, workflow run, actor, environment, and deployment/rollback outcomes form the chain of evidence.

`created_at` is release metadata produced during publishing. Environment-specific `deployed_at`, deployer, environment, previous deployment ID, health result, and rollback reason belong in deployment history, not in the portable release manifest.

Aggregation is atomic at the manifest boundary. A failed build, push, scan, or missing/invalid component result prevents the aggregation job and therefore prevents a deployable manifest. Registry pushes completed before another component fails can remain and are subject to registry lifecycle policy; their existence alone is not a successful release.

## Remote state

`vps-deploy.yml` (DEVOPS-009) uses the dedicated application/environment root registered for each stack in its root-owned host stack registry:

```text
/srv/example/production/
  lock                                   stack-scoped operation lock
  active.json                            authoritative active release record (atomic commit point)
  active-manifest.json                   copy of the active immutable manifest
  previous.json, previous-manifest.json  last superseded successful release
  manifests/<deployment-id>.json         write-once canonical manifest copies
  releases/<deployment-id>/<attempt>/    staged Compose files, generated image override, request record
  history/deployments.jsonl              append-only sanitized records
  runtime/generations.override.json      derived runtime-secret generation labels
  stack.env                              optional operator-owned non-secret interpolation values
```

Updates are locked, staged, and atomically activated; the layout is versioned with the workflow ([operations guide](vps-deployment.md#remote-state)). Application secrets are supplied through the [implemented Doppler host primitive](doppler/vps-bootstrap.md), mounted read-only by Compose, and remain outside GitHub Actions and audit artifacts. Rendered secrets live on restricted tmpfs under `/run/runtime-secrets/<application>/<environment>/<service>/`, as immutable generations behind `pending`, `current`, and `previous`. Deployment history records generation IDs only, never values or value hashes.

## Runtime secret ordering

`vps-deploy.yml` consumes the DEVOPS-007 host interface (systemd lifecycle units and the status/prune CLI) and owns this ordering:

1. Render every registered service's secrets to pending generations before migration. A render failure discards what was rendered and fails the deployment with nothing changed.
2. Activate the migrator's generation only for the migration run. DEVOPS-007 has no deactivate operation, so it stays `current` on tmpfs until a later prune removes older generations or the host reboots.
3. Activate remaining generations (activation itself is not a health verdict).
4. Recreate services whose generation changed: generation ids are container labels, so Compose recreates exactly those containers. Restart alone is not relied upon to retarget a bind mount.
5. Verify application health. On failure, restore retained generations and the previous images, and recreate again.

Restore-after-failure restores the previous images and generations together. `vps-rollback.yml` (not yet implemented) restores image digests and keeps the current secret generation by default, because secrets are environment state.

## Migration, health, and availability

For the backend, the configured DatabaseMigrator image runs as a release-scoped one-shot Compose service (`docker compose run`, bounded by `migration-timeout-seconds`; it belongs in a non-default Compose profile and long-running services must not depend on it). Its explicit successful exit is required before WebAPI, Consumer, or Jobs are released; container health alone is not proof that a migration completed. Failure blocks dependent services, records the failed attempt, and does not run an automatic reverse migration. Next.js stacks leave `migration-service` empty. The current backend template's migrator keeps running after it migrates and reports success through health. It must exit with a status code before it can satisfy this contract ([template findings](doppler/architecture.md#template-findings-that-affect-adoption)).

After migration, Compose service state and configured HTTP endpoints gate activation. Rollback changes application image digests only and is eligible only when the previous application remains compatible with the current database. Expand/migrate/contract schema practices preserve that window.

A single VPS cannot provide host-level high availability: host failure, Docker daemon restart, shared reverse-proxy failure, resource exhaustion, or some updates can interrupt every stack. Health gates reduce bad-release exposure but do not eliminate deployment downtime. Multi-host orchestration and server provisioning/Terraform remain outside this ticket.

## Schema evolution

`schema_version` uses `MAJOR.MINOR`:

- A minor schema revision may add optional fields. Readers must ignore unknown optional fields after validating the supported core.
- A major schema revision changes required meaning or removes/renames fields. A new toolkit major version must provide a migration or dual-read period.
- Writers emit the lowest schema version that represents the release. Readers reject unsupported major versions before any remote mutation.
- Existing manifests are never rewritten in history. Migration records point from an old canonical hash to a new representation when conversion is necessary.

Toolkit SemVer and manifest schema versions are related but independent: a toolkit minor can add support for an optional manifest field, while a manifest major change normally requires a toolkit major compatibility decision.
