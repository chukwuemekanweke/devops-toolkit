# Versioning and compatibility

Toolkit releases follow Semantic Versioning. Workflow filenames and their documented inputs, outputs, secret names, permission needs, manifest formats, defaults, and observable failure behavior form the public API.

The application image-configuration schema and generated release-manifest schema are separately versioned public contracts. A toolkit release declares which versions it reads and writes.

## Change classification

### Major

A major release is required for removing or renaming a workflow/input/output, changing an input's meaning or default incompatibly, adding a required input or secret to an existing path, increasing required permissions materially, changing established output/manifest formats incompatibly, or introducing breaking execution/failure behavior.

### Minor

A minor release may add an optional input, add an output, support another registry or topology under existing semantics, add a compatible manifest field, or provide an opt-in compatible enhancement. New behavior that could surprise existing callers defaults off unless it is a clearly safe correction.

### Patch

A patch release contains backward-compatible bug, security, documentation, validation, or maintenance fixes that preserve the public contract. A security fix that cannot preserve compatibility may require a new major release and an advisory rather than being mislabeled as a patch.

## Tags and consumer pins

- `v1.2.3` is an immutable release tag and must never be moved.
- `v1` is a mutable major alias advanced only to a validated release compatible with every supported v1 contract.
- A full commit SHA is immutable and provides strongest workflow-code reproducibility.
- `main` is development state and is never the recommended production reference.

Most consumers may use `@v1` for compatible fixes. Regulated, production-critical, or tightly controlled consumers should use `@v1.2.3` or a full SHA and update deliberately.

## Advancing `v1`

1. Merge a reviewed change with contract classification recorded.
2. Pass syntax, schema, unit/behavior, security, and representative caller validation.
3. Update documentation and `CHANGELOG.md`.
4. Create and verify the immutable release tag.
5. Test reference consumers against that exact tag, including four-image and multi-workspace cases where affected.
6. Obtain release approval.
7. Move `v1` to the already-validated release commit using the protected release process.
8. Verify the remote tag target and publish release notes.

No tags are created or moved by DEVOPS-001.

DEVOPS-002 adds validation and documents promotion but intentionally creates no release tag: none of the five public reusable capabilities is usable yet. Releases are prepared only after a real workflow has its applicable contract, behavior, negative, and consumer smoke tests passing. Tag creation and movement remain explicit maintainer operations; validation never advances `v1` automatically.

## Release validation checklist

- Every workflow parses and exposes only supported `workflow_call` types.
- Required/optional inputs, defaults, outputs, secrets, and minimum permissions match documentation.
- Examples parse and use job-level reusable workflow invocation correctly.
- Existing contract fixtures and representative consumer scenarios pass.
- Secret-dependent behavior fails closed and logs/artifacts contain no secret values.
- Third-party dependencies are reviewed and pinned.
- Manifest writers/readers and remote-state compatibility tests pass.
- Image configuration v1 validates both four-component backend and three-component frontend fixtures, including rejection cases.
- Failure, cleanup, concurrency, first-deploy, multi-image, partial-publish, health-failure, and rollback paths are exercised as applicable.
- Security and change classification reviews are complete.
- Changelog and migration guidance are current.

## Introducing v2

`v2` is implemented and released alongside v1. Existing v1 files/tags remain available and receive critical compatible fixes for a published support window. Breaking workflow filenames or v2 schema readers are added without moving `v1`. Migration documentation maps every changed input, secret, permission, output, and behavior; consumers migrate and validate independently. Only `v2` points to v2 releases. Deprecation does not silently repoint or delete `v1`.

## Image and release schema evolution

Image configuration `schemaVersion: 1` is read from caller repositories; release manifest `schema_version: "1.0"` is generated by publishing. Adding an optional field with a stable default can ship in a toolkit minor after both reference fixtures pass. A field removal/rename, changed meaning/default, or new required field is breaking. The toolkit must never silently reinterpret an existing version number.

When a new schema major is needed, readers should support the old and new forms during an announced migration window where safe. Writers continue emitting the old form for `v1`; the new toolkit major emits the new form. Consumer config migration and historical manifest/remote-state migration are separate, documented operations.

## Deprecation and consumer expectations

Deprecations are announced in the changelog and migration guide, include a supported replacement, and remain functional for the current major line. Consumers own periodic pin updates, compatibility testing, environment policy, and migration before end of support. The maintainer owns clear notices, stable tags, critical security communication, and a reasonable overlap for supported majors.
